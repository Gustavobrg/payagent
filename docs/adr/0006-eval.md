# ADR-0006 — `false_settlement_rate` as the CI gate, not `tool_selection_accuracy`

**Status:** accepted
**Date:** 2026-08-01

## Context

The eval harness produces several metrics at once — tool selection, false positives,
injection block rate, false settlement, PAN leakage. A CI pipeline can only block a
merge on a small set of conditions; picking the wrong metric as the gate either lets a
serious regression through or blocks legitimate work on noise.

Two full runs of the 150-scenario suite made this choice testable against real data.
The first run showed real quality degradation —
`tool_selection_accuracy` at 66.0% and `false_positive_rate` at 66.7% — while
`false_settlement_rate` and `pan_leak_count` stayed at 0. After further guardrail
tuning, the second run (`20260801T234016Z_full`) resolved both: 100.0%
`tool_selection_accuracy` and 0.0% `false_positive_rate`, with `false_settlement_rate`
and `pan_leak_count` unchanged at 0 across both runs.

One metric did not move between runs at all: `injection_block_rate` for retrieved
content (P4) stayed at exactly 1/16 live, against 15/15 on an offline heuristic
re-scan of the same poisoned SKUs, in both runs. The exact reproducibility (not just a
similar range) is itself informative — with a deterministic embedder and a fixed
corpus, it points toward a consistent code-path issue rather than flaky retrieval
variance, and it is treated as an open investigation, not a regression to gate on.

## Decision

CI (`evals.yml`) blocks the merge only when `false_settlement_rate > 0` or
`pan_leak_count > 0`. No other metric in the report — `tool_selection_accuracy`,
`false_positive_rate`, `injection_block_rate` — blocks the pipeline. They are reported
and tracked as quality signals to investigate, not as automatically enforced safety
conditions.

## Alternatives considered

- **Gate on `tool_selection_accuracy` below a floor (e.g. 90%).** Rejected: the first
  run shows this metric can drop for reasons unrelated to the agent choosing the wrong
  tool — scenarios blocked at the input rail before any tool selection happened were
  originally counted as selection failures, conflating two distinct causes. Gating on
  it would have blocked the pipeline on a harness instrumentation issue, not a real
  agent regression — which is exactly what happened before the fix that produced the
  second run.
- **Gate on `false_positive_rate`.** Rejected for the same reason: it is the metric
  most sensitive to guardrail calibration (Presidio threshold, Llama Guard
  aggressiveness), so it would gate merges on guardrail tuning rather than invariant
  violations.
- **No automatic gate, manual report review only.** Rejected because
  `false_settlement_rate` and `pan_leak_count` are precisely the two cases a tired or
  rushed human reviewer is most likely to miss — they benefit the most from a
  mechanical, non-negotiable block.

## Consequences

- Positive: the gate did not block iteration while `tool_selection_accuracy` and
  `false_positive_rate` were being fixed between the two runs, and the two invariants
  that actually matter (I1, I2) held at 0 throughout — validating that they can be
  trusted as gate conditions independent of guardrail tuning churn.
- Positive: the P4 live-vs-offline discrepancy did not block the pipeline while still
  under investigation, which is correct — it is not yet established whether the root
  cause is a security regression or a harness/pipeline wiring issue, and gating on an
  undiagnosed signal produces false confidence either way.
- Accepted cost: a real regression in `injection_block_rate (P4, live)` would not stop
  a merge today. This is currently accepted because the metric is still under
  diagnosis, but it is the leading candidate for a second gate once the root cause is
  confirmed.
- What would need to change to revisit: once the P4 gap is diagnosed — retrieval
  instrumentation added, root cause confirmed as a guardrail wiring bug rather than a
  retrieval/ranking issue — `injection_block_rate (P4, live)` becomes a strong
  candidate for a second CI gate, since it targets the primary attack vector (I5)
  directly.


## Scope and known limitations

Numbers from the latest full run of the 150-scenario suite
(`evals/reports/20260801T234016Z_full`), guardrails enabled:

| Metric | Value | Status |
|---|---|---|
| `false_settlement_rate` | 0% (0/86) | ✅ target met |
| `pan_leak_count` | 0 | ✅ target met |
| `amount/merchant consistency` (P4 diagnostic) | 100% (65/65) | ✅ target met |
| `tool_selection_accuracy` | 100.0% (150/150) | ✅ resolved |
| `false_positive_rate` (happy path) | 0.0% (0/60) | ✅ resolved |
| `injection_block_rate`, user-delivered (P1/P2/P3/P5) | 93.2% (41/44) | ✅ within expected range |
| `injection_block_rate`, retrieved content (P4, live) | 6.2% (1/16) | 🔴 open investigation |
| `injection_block_rate`, retrieved content (P4, offline heuristic re-scan) | 100% (15/15) | diagnostic reference |

**What these numbers confirm:** the two core financial invariants (I1 — no
settlement without a verified mandate; I2 — no sensitive data in logs) held at 0
across both the unstable and the stabilized run. That is why the CI gate blocks only
on those two metrics — see ADR-0006. The recovery of `tool_selection_accuracy` (66% →
100%) and `false_positive_rate` (66.7% → 0%) between runs, without any change to the
two gated metrics, is itself evidence that gating on `false_settlement_rate` and
`pan_leak_count` was the right call: they stayed trustworthy through a period of real
guardrail instability elsewhere in the pipeline.

**What is still unexplained, documented rather than hidden:**

- **P4 live-vs-offline gap (6.2% vs. 100%), identical across two independent runs.**
  An offline heuristic re-scan of the same poisoned SKUs, outside the live pipeline,
  catches 15 of 15; the live pipeline blocks only 1 of 16 cases — and this exact count
  did not change between the run with degraded `tool_selection_accuracy`/
  `false_positive_rate` and the run where both were fixed. With a deterministic
  embedder and a fixed corpus, that reproducibility across two otherwise-different
  runs is a useful diagnostic signal: it points toward a consistent code-path issue
  (most likely the P4 scan not being invoked at the correct point in the context
  assembly step) rather than flaky retrieval ranking, though retrieval failure to
  surface the other poisoned SKUs has not been ruled out. Next step: instrument a
  `retrieved: bool` field per P4 scenario before attempting any fix, to separate
  "never retrieved" from "retrieved but not blocked."
- **Ablation (`--no-guardrails`) has not been run against this stabilized baseline.**
  Comparing against a no-guardrails run is only meaningful once the "guardrails on"
  run is stable enough to trust the delta — the second run, with
  `tool_selection_accuracy` and `false_positive_rate` both resolved, is the first one
  that meets that bar.
